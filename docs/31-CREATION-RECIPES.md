# Creation Recipes

## Purpose

Creation Recipes are the narrative equivalent of a scaffolding template.

They answer:

> How should a new project of this class be initialized?

They are NOT a generic workflow DSL.

## Uses

A recipe drives:
- `narrative init --recipe ...`
- Control Plane `Create` wizard.

One source, two user interfaces.

## Layout contract

Every recipe lives under `recipes/<id>/` with this fixed structure:

```text
recipes/<id>/
├── recipe.yaml           # creation-recipe/v1 schema; declares metadata, parameters, project
├── parameters.schema.json # JSON Schema 2020-12; user-supplied parameter contract
├── ui.schema.json        # optional RJSF uiSchema hints for the wizard
├── skeleton/             # templated starter files; rendered by the mustache-subset engine
│   ├── narrative.yaml    # project manifest; substituted with {{title}}, {{projectId}}, etc.
│   ├── profiles/        # audience profiles resolved from specs/profile-aliases.yaml
│   ├── canon/           # story content skeleton (characters, chapters)
│   ├── packs/           # pack instruction stubs (story_core, visual, editorial, etc.)
│   └── goals.yaml       # initialGoals list
├── recipe.lock.json     # SHA-256 lock of recipe.yaml + parameters.schema.json + skeleton/
├── README.md            # recipe documentation
└── tests/               # recipe-level integration tests (optional)
```

`recipe.lock.json` is generated by `python tools/validate-recipes/validate.py --publish recipes/<id>/`
and committed alongside the recipe. It records `recipeYamlSha256`, `parametersSchemaSha256`,
`skeletonFileShas256`, and `generatorVersion`. The validate script rejects any recipe whose
lock fingerprint does not match its current content (REQ-CR-1b).

## Contents

## Recipe declares

- metadata;
- supported format;
- parameter JSON Schema;
- profile defaults;
- packs;
- skills;
- publishing targets;
- project skeleton;
- initial goals/checklist.

It does NOT embed arbitrary Python or JavaScript.

## Example flow

```text
Create
  |
  +-- Illustrated Middle Grade
  |
  +-- Audience 10–11
  |
  +-- Fantasy + Mystery
  |
  +-- Local preferred images
  |
  +-- Print PDF
  |
```

## Security

### Mustache-subset grammar pinning (Decision 3)

Skeleton files use a restricted mustache-subset grammar. The grammar is **parsed, not eval'd**.
The template engine REJECTS the following patterns at parse time with `TemplateError`:

| Forbidden pattern | Error code | Reason |
|---|---|---|
| `{{> partial}}` | `forbidden-partial` | No file-system partials |
| `{{{ raw }}}` | `forbidden-raw` | No raw HTML injection vector |
| `{{ a.b.c }}` | `forbidden-dotted-path` | No arbitrary property access |
| `{{ {{nested}} }}` | `forbidden-nested` | No nested variable names |
| `{{ upper(name) }}` | `forbidden-function-call` | No function invocations in templates |

All substitutions are HTML/JSON-escaped by default. The grammar is implemented identically
in Python (`tools/narrative_recipes/template_engine.py`) and TypeScript
(`control-plane/src/recipes/templateEngine.ts`); both implementations satisfy the same
5-fixture test corpus and round-trip to the same canonical JSON output.

### Untrusted recipe data
- validate against schema;
- never execute scripts;
- never install dependencies automatically;
- external provider enabling requires explicit user action.

## Recipe inheritance

Avoid sophisticated inheritance in V1.

If repeated configuration becomes painful, allow:
- `extends: recipe-id`

only after a spike defines deterministic merge semantics.

## Relationship to ActiveGraph

Recipe initializes state/config.

ActiveGraph behaviors manage subsequent reactive evolution.

Do not model every narrative production step in the recipe.

## Recipe catalog

The Control Plane MAY display:
- title;
- target audience;
- format;
- profiles;
- expected outputs;
- capabilities required.

## Acceptance

A recipe is good if a user can create a valid project without knowing the
internal directory schema.
